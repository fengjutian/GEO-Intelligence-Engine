# GEO Intelligence P0 V1.99 增量记录

> 状态：已记录｜日期：2026-11-15｜前置基线：V1.98，待项目负责人确认

## 告警接入通知渠道

- `raiseSignal` 在落库后调用既有 `notify.Notifier`（webhook / SMTP，配置项 `GEO_ALERT_WEBHOOK_URL`、`GEO_SMTP_*`）。
- 通知载荷沿用监控告警的结构：`{alertId, projectId, scheduleId, kind, message}`，信号类告警的 `scheduleId` 为空。
- 通知失败不影响告警落库（返回结果被忽略）。

## 告警定时检查

- `StartSignalLoop` 随 API 启动，默认每 **6 小时**评估一次（`GEO_SIGNAL_INTERVAL_MINUTES`，最小 5 分钟），启动时立即跑一轮。
- 评估范围从"有审计的项目"改为**全部项目**，否则只有站点日志、没有审计的项目永远不会触发 `crawler_silent`。

## 实测

用本地 HTTP 监听器（`127.0.0.1:9099`）接收，验证真实投递：

| 告警 | 项目 | 投递 |
|---|---|---|
| `share_drop`：份额 50% → 0% | 回归测试项目 | 收到 |
| `crawler_silent`：近 7 天无 AI 抓取 | 仅有 30 天前 GPTBot 记录的项目 | 收到 |

收到的载荷示例：

```json
{"alertId":"e9181c63-...","projectId":"01a1df2d-...","scheduleId":"","kind":"crawler_silent","message":"近 7 天没有任何 AI 爬虫访问，此前有抓取记录"}
```

证据：`.run/geo-signal-notify-verification.json`

## 已知边界

- 通知渠道是全局配置，尚未按项目/租户区分接收人；
- 循环未做分页与限流，项目数 > 500 时只覆盖前 500 个；
- 通知结果不落库，无法回溯"这条告警是否送达"；
- `share_drop` 仍只比较同提示口径的最近两次审计。
