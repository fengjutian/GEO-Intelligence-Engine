## 1. 文档目的

本文将技术规划转化为可设计、可开发、可测试、可验收的产品需求。目标不是承诺操控任何 AI 平台的推荐结果，而是建立一套可复现的采集、评估、诊断、优化和实验体系，持续提升品牌信息被发现、正确理解、引用和推荐的概率。

## 2. 产品定义

### 2.1 产品愿景

GEO Intelligence 是企业的品牌知识与 AI 搜索智能基础设施，形成如下闭环：

`Discovery → Understanding → Intelligence → Optimization → Execution → Evaluation`

### 2.2 核心价值

1. 发现：识别网站、外部来源和 AI 搜索场景中的品牌信息。
2. 理解：建立品牌、产品、能力、场景、客户和证据之间的实体关系。
3. 测量：持续、可复现地测量品牌提及、推荐、引用和情感表现。
4. 诊断：解释品牌缺席、误解、未被引用或输给竞品的可能原因。
5. 行动：把问题转化为有依据、有优先级、可审核的优化任务。
6. 验证：使用固定测试集、重复采样和对照实验评估变化。

### 2.3 产品原则

- 不把 GEO 简化为关键词排名。
- 提及、推荐、引用、正向提及必须分别统计。
- 单次回答不能代表长期可见度。
- Schema/JSON-LD 是理解信号，不是推荐保证。
- 不制造虚假媒体、评价、引用或外链。
- 原始证据与算法派生结果分离、可追溯、可重算。
- 所有生产修改必须经过权限校验、差异审核并支持回滚。
- 明确区分模型 API 输出与消费者产品真实搜索结果。

## 3. 成功标准与边界

### 3.1 北极星指标

在固定问题集、引擎、模型版本、地区、语言和采样协议下，产生有效、可复现的品牌可见度测量，并能把低表现问题转化为带证据的可执行任务。

### 3.2 首期成功标准

- 用户能在 15 分钟内创建项目并启动首次审计。
- 审计完整保存网页快照、问题、模型参数、原始回答、引用和评估版本。
- 对有效回答准确计算 Mention、Recommendation、Citation、Positive Mention 四类指标。
- 报告中的每个结论可下钻到原始页面或原始 AI 回答。
- 同一评估算法可对历史原始回答重新运行，且不覆盖旧结果。
- 失败任务可重试；部分失败不会使全部审计结果不可用。

### 3.3 明确不承诺

- 不承诺特定 AI 平台一定收录、引用或推荐客户品牌。
- 不推断或宣称掌握第三方模型未公开的内部检索/排序机制。
- 不把 API 响应等同于 ChatGPT、Perplexity、Gemini 等消费者产品界面结果。
- P0 不自动修改或发布客户生产内容。

## 5. 核心业务流程

### 5.1 首次 GEO Audit

1. 用户创建组织和项目。
2. 填写品牌名称、别名、官网、地区、语言、行业、产品和竞品。
3. 系统验证网站所有权或由管理员明确标记为公开审计。
4. 系统读取 robots.txt、sitemap，并受控抓取页面。
5. 系统抽取品牌与产品实体，用户确认或修正。
6. 系统生成买家问题，用户可增删、编辑和分组。
7. 用户选择 AI 引擎、地区、语言、采样次数和预算后启动审计。
8. 系统采集原始回答，解析提及、推荐、引用和情感。
9. 系统计算指标、识别问题并生成报告。
10. 用户把报告建议转换为优化任务。

### 5.2 持续监测

用户创建日/周/月计划；系统冻结测试协议版本，按计划重复采样；结果按可比口径生成趋势、异常和变化通知。模型或协议发生变化时必须在趋势图中标记断点。

### 5.3 优化与验证（P2/P3）

诊断生成任务 → 人工或 Agent 产出草稿 → 自动校验 → Diff 审批 → 合并/发布 → 冷却期 → 对照实验 → 结论 → 保留或回滚。

## 7. 数据需求

### 7.1 核心实体

首期至少包含：organizations、users、memberships、projects、brands、brand_aliases、products、entities、entity_relations、competitors、websites、crawl_runs、website_pages、website_contents、buyer_questions、query_clusters、ai_engines、audit_tasks、ai_requests、ai_responses、evaluation_runs、answer_evaluations、citations、brand_mentions、visibility_metrics、content_gaps、optimization_tasks、audit_logs、experiments、experiment_samples。

### 7.2 数据设计约束

- 所有业务表带 `tenant_id` 或可通过外键严格追溯租户。
- 原始内容、原始回答、评估结果、聚合指标分别存储。
- 原始记录采用追加写；更正通过新版本或纠错记录完成。
- 每条派生结果记录输入 ID、算法版本、配置哈希和生成时间。
- 网页正文、截图、大响应放入 S3 兼容对象存储；数据库保存 URI、哈希、大小和 MIME。
- 时间统一存 UTC，界面按项目时区展示。
- URL 保存原始值、规范化值和最终重定向值。
- 敏感密钥只保存密钥管理系统引用，不进入业务表或日志。

### 7.3 关键状态

- 审计：draft、queued、running、partial_success、succeeded、failed、cancelled。
- 抓取：discovered、queued、fetched、rendered、parsed、blocked、failed。
- 评估：pending、machine_evaluated、needs_review、human_verified、superseded。
- 优化任务：todo、in_progress、in_review、done、rejected、cancelled。
- Agent 执行：planned、awaiting_approval、running、succeeded、failed、rolled_back、cancelled。

### 7.4 保留与删除

- 默认长期保存原始 AI 回答以支持复算；具体期限由套餐与合同配置。
- 用户删除项目进入软删除和冷静期；到期后删除数据库与对象存储数据并生成删除记录。
- 法律保留、备份清除周期及数据导出需在企业合同中明确。

## 8. 算法与测量规范

### 8.1 有效回答

有效回答须满足：请求成功、非空、非纯错误/拒答、未严重截断、语言符合协议且可被解析。有效性规则必须版本化；被排除回答仍保留并在质量面板中统计。

### 8.2 指标口径

对一个固定分析切片，设有效回答集合为 `R`：

- `Mention Rate = count(r∈R 且提及品牌) / |R|`
- `Recommendation Rate = count(r∈R 且主动推荐品牌) / |R|`
- `Official Citation Rate = count(r∈R 且引用品牌自有域名) / |R|`
- `Positive Mention Rate = count(r∈R 且正向提及) / count(r∈R 且提及品牌)`

同一回答多次提及在“回答率”指标中只计一次；提及次数作为单独的频次指标。跨问题汇总默认按回答等权，同时提供按问题等权视图，避免采样次数不同造成偏差。

### 8.3 置信与校准

- 比例指标使用 95% Wilson 置信区间。
- Judge 上线前需在人工标注集上分项评估；核心提及识别目标 F1 ≥ 0.95，推荐/引用分类目标 F1 ≥ 0.85。
- 未达到目标时必须进入人工复核或在报告中展示低置信提示。
- 综合评分权重只能通过版本化配置启用，且报告必须展示分项，不允许只展示黑盒总分。

## 9. 非功能需求

### 9.1 性能与容量（P0 基线）

- 常规 API P95 响应时间 ≤ 500 ms（不含外部模型/抓取任务）。
- 报告查询 P95 ≤ 2 s；大导出采用异步任务。
- 单项目支持至少 10,000 页面、1,000 问题和每次审计 20,000 个模型响应。
- Worker 可水平扩展；限流按供应商、租户和项目分别控制。

### 9.2 可用性与可靠性

- 正式版月度可用性目标 99.9%，计划维护除外。
- 队列任务至少一次投递，业务处理必须幂等。
- 外部依赖失败采用熔断、退避和隔离；部分供应商失败产生 partial_success。
- 数据库每日全量备份并进行增量日志备份；目标 RPO ≤ 24 小时、RTO ≤ 4 小时（MVP）。

### 9.3 安全

- TLS 传输；数据库、对象存储和备份静态加密。
- 密码采用行业标准强哈希；支持 MFA（企业版应支持 SSO/SAML/OIDC）。
- API Key 加密托管、界面脱敏、可轮换、最小权限。
- 防 SSRF：抓取器禁止访问 loopback、链路本地、私网、云元数据地址，并在每次重定向后重新校验。
- 防提示注入：网页内容视为不可信数据，不得覆盖系统指令或触发工具/发布动作。
- 所有登录、权限变更、密钥操作、导出、审批、发布、回滚写入不可变审计日志。

### 9.4 合规与伦理

- 遵守 robots.txt、站点条款、版权、速率限制和适用隐私法规。
- 默认最小化采集个人信息；检测到敏感信息时支持脱敏和删除请求。
- 外部内容只保存分析所需范围和证据，不把受版权保护内容整库再发布。
- 明确禁止生成虚假评价、媒体报道、研究、客户案例或伪造引用。

### 9.5 可观测性

- 日志包含 trace_id、tenant_id、project_id、job_id，但不得包含密钥和完整敏感正文。
- 监控任务积压、成功率、外部 API 错误率、延迟、成本、抓取状态和 Judge 质量漂移。
- 对预算超限、任务持续失败、数据异常和模型版本变化告警。

### 9.6 可访问性与国际化

- Web 界面目标符合 WCAG 2.1 AA。
- P0 支持简体中文和英文内容分析；界面文案可国际化。
- 所有日期、数字和货币按用户/项目 locale 展示。

## 10. 外部接口需求

### 10.1 API 原则

- REST API 以 `/api/v1` 版本化；异步操作返回 job ID。
- 创建类接口支持 Idempotency-Key。
- 列表接口统一游标分页、筛选和排序。
- 错误返回稳定 error_code、用户可读信息、trace_id 和可重试标记。
- Webhook 采用签名、时间戳和重放保护，并支持投递重试与死信查看。

### 10.2 主要资源

`/projects`、`/brands`、`/competitors`、`/crawls`、`/pages`、`/entities`、`/questions`、`/audits`、`/responses`、`/evaluations`、`/metrics`、`/reports`、`/content-gaps`、`/optimization-tasks`、`/experiments`、`/integrations`。

### 10.3 集成

- P0：模型供应商 API、S3 兼容对象存储、邮件通知。
- P1：搜索/外部数据源、Webhook。
- P3：GitHub App，按仓库授权，禁止请求用户全局 Personal Access Token 作为默认方案。

## 12. P0 交付范围与验收门槛

### 12.1 P0 必须交付

- 组织/项目/品牌/竞品基本管理。
- robots/sitemap/静态与 JS 网页抓取和基础技术审计。
- 品牌、产品、Schema 和基础关系抽取及人工确认。
- Buyer Question 生成、编辑、聚类。
- 至少两个模型供应商的统一调用、预算和任务编排。
- 原始回答长期保存、有效性判断、提及/推荐/引用/情感评估。
- 四类核心指标、置信区间、切片和证据下钻。
- GEO Audit 报告、PDF/CSV 导出和优化任务创建。
- RBAC、租户隔离、审计日志、基础监控和备份。

### 12.2 发布门槛

- 所有 Must 需求通过验收测试。
- P0 核心流程端到端成功率 ≥ 95%（排除已确认的外部供应商故障）。
- 无 P0/P1 级安全漏洞；租户隔离测试 100% 通过。
- Mention Judge F1 ≥ 0.95；Recommendation/Citation Judge F1 ≥ 0.85，或启用强制人工复核降级方案。
- 指标可由保存的原始响应和评估结果独立重算并一致。
- 完成灾备恢复演练、预算熔断测试和任务幂等测试。

## 14. 商业版本建议

| 能力 | 免费版 | 专业版 | 企业版 |
|---|---|---|---|
| 项目/站点 | 1/1 | 配额内多个 | 多组织、多品牌、多区域 |

## 15. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 模型输出随机且版本不可控 | 趋势误判 | 固定协议、重复采样、版本快照、置信区间和断点标记 |
| 消费者应用无稳定 API | 测量代表性不足 | 区分渠道；只使用合规授权的采集方式；报告披露限制 |
| Judge 误判 | 指标失真 | 标注集、分项 F1、置信阈值、人工复核、版本化重算 |
| 抓取触发法律或站点限制 | 合规风险 | robots/条款/速率治理、域名白名单、删除机制 |
| 网页提示注入/SSRF | 系统安全风险 | 内容与指令隔离、网络出口策略、重定向逐跳校验 |
| 模型调用成本失控 | 毛利和体验受损 | 预估、配额、硬上限、缓存、去重和熔断 |
| 自动生成事实或引用错误 | 品牌与法律风险 | 来源绑定、事实校验、人工审批、禁止无证据发布 |
| 指标被“刷”高 | 产品价值受损 | 固定测试集、异常检测、原始证据、禁止自报无验证来源 |

## 16. 待产品评审决策

以下事项原文未给出确定答案，应在详细设计前决策并形成 ADR/产品决策记录：

1. 首发目标客户是 SaaS/AI 公司，还是通用企业品牌；这将决定问题模板和实体模型深度。
2. 首发支持哪些模型供应商、搜索渠道、语言和地区。
3. P0 是否只做客户自有站点，还是包含公开竞品站点抓取。
4. 网站所有权验证规则及“公开审计”的合法边界。
5. 原始回答、网页快照和外部内容的默认保留期限。
6. Judge 采用规则、LLM 还是混合方案，以及人工标注集规模。
7. 免费版的调用配额、防滥用机制和报告公开分享策略。
8. 企业版合规目标（例如等保、SOC 2、ISO 27001）及落地时间。
9. 消费者应用真实结果的合规采集方式；没有授权渠道时不得列为 P0 承诺。
10. Phase 1 的目标吞吐、预算和正式 SLA，需结合试点客户数据校准。
