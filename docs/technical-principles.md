# GEO Intelligence 技术原理

> 版本：V1.0  
> 日期：2026-11-13  
> 关联文档：[详细产品需求文档](./product-requirements.md)

## 1. 技术本质

GEO Intelligence 不是通过猜测或操控第三方 AI 的内部排名算法来保证品牌曝光，而是建立一套可追溯、可重复、可验证的工程系统：采集品牌相关证据，建立品牌知识模型，在受控条件下测量 AI 搜索表现，诊断信息缺口，执行经过审核的优化，再通过持续实验验证效果。

完整闭环为：

```text
网站与外部信息采集
        ↓
品牌实体和知识关系建模
        ↓
买家问题生成与 Query Fan-out
        ↓
多 AI 引擎重复测试
        ↓
提及、推荐、引用和情感分析
        ↓
内容、语义与权威性缺口诊断
        ↓
生成并执行优化任务
        ↓
对照实验与持续效果验证
```

对应产品闭环：

`Discovery → Understanding → Intelligence → Optimization → Execution → Evaluation`

## 2. 信息发现原理

### 2.1 网站发现

系统从企业官网和被授权的数据源开始，模拟搜索引擎的基础发现过程：

1. 获取并解析 `robots.txt`，判断不同 User-Agent 的访问权限。
2. 读取 `sitemap.xml` 及其嵌套索引，发现候选 URL。
3. 通过站内链接继续发现页面，并形成链接关系图。
4. 对 URL 进行规范化，处理参数、Canonical 和重定向。
5. 在规定的域名、深度、并发和速率范围内执行抓取。

抓取系统必须遵守 robots 规则、站点条款和速率限制，不能把技术上能够访问等同于允许无限制采集。

### 2.2 页面解析

系统分别保存原始 HTML 和 JavaScript 渲染后的 HTML，并从中提取：

- 页面标题、描述、标题层级和正文。
- Canonical、语言、发布时间和更新时间。
- 内链、外链、图片、视频与音频信息。
- Schema.org、JSON-LD 等结构化数据。
- HTTP 状态、重定向链和内容哈希。

对比静态 HTML 与渲染结果，可以发现主要内容是否依赖 JavaScript，以及普通爬虫或 AI 抓取系统是否可能看不到关键内容。

### 2.3 技术可发现性判断

系统通过规则识别影响发现与理解的问题，例如：

- `robots.txt` 阻断或页面带有 `noindex`。
- 页面返回非 2xx 状态或存在重定向循环。
- Sitemap 缺失、错误或包含失效 URL。
- Canonical 缺失、冲突或指向错误页面。
- 页面只能在复杂交互之后加载正文。
- 页面缺少有效站内链接，形成孤立页面。
- 同一内容通过多个参数 URL 重复暴露。

这一阶段解决的是“内容是否可能被发现和解析”，并不直接证明第三方 AI 已经收录该内容。

## 3. 品牌知识建模原理

### 3.1 实体抽取

系统从网页正文、结构化数据和外部来源中识别实体，例如：

- Organization：企业或组织。
- Brand：品牌。
- Product：产品。
- SoftwareApplication：软件应用。
- Feature：功能或能力。
- Technology：所使用或支持的技术。
- Industry：行业。
- Audience：目标客户。
- UseCase：应用场景。

每个实体必须保留规范名称、别名、类型、属性、来源片段、抓取时间和置信度。

### 3.2 实体消歧

同一名称可能代表不同对象，同一对象也可能存在多个名称。系统综合以下信号进行消歧：

- 名称和别名相似度。
- 官方域名与 `sameAs` 关系。
- 产品所属组织。
- 页面上下文与共现实体。
- 地区、行业和产品属性。
- 人工确认结果。

低置信度实体不能自动合并；人工执行的合并和拆分必须可撤销并保留审计记录。

### 3.3 知识关系

系统将孤立实体组织为带来源证据的知识关系：

```text
品牌 → 产品 → 功能 → 技术
              ↓
         行业 → 客户 → 应用场景
```

关系不能仅保存结论，还要保存支持该结论的页面、结构化数据或外部来源。这样才能解释系统为什么认为某产品具有某项能力。

### 3.4 一致性检查

系统比较官网不同页面、结构化数据和第三方来源中的品牌事实，识别：

- 名称、定位或产品归属不一致。
- 功能、价格、版本或部署方式冲突。
- 已下线产品仍被外部页面描述为当前产品。
- JSON-LD 与用户可见正文不一致。
- 第三方对品牌的描述与官方表述存在明显偏差。

一致性越高，机器系统越容易形成稳定的实体理解；但一致性本身不构成被推荐的保证。

## 4. Query Fan-out 原理

用户通常只输入一个简短问题，而 AI 搜索系统可能围绕问题隐含的多个方面进行检索和综合。Query Fan-out 用于模拟和覆盖这种问题扩展。

例如：

```text
原始问题：哪个 AI 开发平台比较好？

可能扩展为：
- 企业 AI 开发平台有哪些？
- 哪些平台适合开发 AI Agent？
- 哪些平台支持私有化部署？
- 开源框架与商业平台有什么差别？
- 不同平台的价格和使用成本如何？
- 企业应该如何选择 AI 开发平台？
```

处理过程如下：

1. 判断问题的语言、主题和用户意图。
2. 抽取品牌、产品、行业等核心实体。
3. 按定义、比较、价格、能力、部署、风险、行业和场景等维度扩展。
4. 对扩展问题进行语义去重和聚类。
5. 保存原始问题与扩展问题之间的父子关系。
6. 将问题映射到网站页面和内容片段。
7. 标记已覆盖、部分覆盖、未覆盖和证据不足的主题。

Query Fan-out 的价值是建立完整的问题空间，而不是机械生成大量近义关键词。

## 5. 多模型测量原理

### 5.1 固定测试协议

为了使不同批次结果具有可比性，每次测试都必须记录并尽可能固定：

- 问题文本及问题集版本。
- AI 引擎、模型及可获得的模型版本。
- 系统提示、温度和其他请求参数。
- 地区、语言和时间。
- 测试渠道和采样次数。
- 采集器及评估算法版本。

模型或协议发生改变时，趋势图必须标记断点，不能把不同条件下的变化直接解释为 GEO 优化效果。

### 5.2 渠道隔离

系统必须区分三类数据：

| 渠道 | 含义 | 限制 |
|---|---|---|
| `model_api` | 直接调用大模型 API | 可能不包含消费者搜索产品的检索和排序逻辑 |
| `search_api` | 调用带搜索能力的正式 API | 行为受 API 产品能力和参数约束 |
| `consumer_app_capture` | 合规采集消费者应用实际结果 | 受授权方式、账户、地区和产品界面影响 |

三种渠道不能直接混合计算总指标。尤其不能把普通模型 API 的回答宣称为 ChatGPT 等消费者产品中的实际搜索表现。

### 5.3 重复采样

生成式模型具有随机性。同一问题在相同条件下也可能产生不同回答，因此系统需要多次采样，并保存每一次原始结果。

单次回答只是一条观察值，不能代表长期品牌可见度。可靠结论需要足够样本、重复测试和不确定性分析。

### 5.4 原始证据保存

每次调用至少保存：

- 完整请求与请求参数。
- 供应商原始响应。
- 模型标识、渠道和采集时间。
- 地区与语言。
- Token、成本、延迟和错误信息。
- 引用 URL 和其他返回元数据。

原始回答与派生评估必须分开存储，使后续算法升级后可以重新评估历史数据，而不需要重新请求第三方模型。

## 6. Answer Judge 原理

Answer Judge 将非结构化 AI 回答转换为可计算的结构化结果。

### 6.1 品牌提及识别

系统综合品牌正式名、别名、产品名和上下文识别品牌出现，并保存：

- 匹配文本及字符位置。
- 关联实体。
- 匹配方式与置信度。
- 支持判定的上下文片段。

单纯字符串匹配容易把同名普通词或其他组织误判为品牌，因此必须结合实体和上下文进行消歧。

### 6.2 推荐识别

品牌出现不等于品牌被推荐。系统需要区分：

- 主动建议用户选择该品牌。
- 将品牌列为候选方案。
- 仅作背景介绍或事实提及。
- 作为负面示例、限制条件或不适合方案出现。

只有具有明确建议语义的回答才能计入推荐。系统同时记录推荐顺序、列表位置、是否为首选以及同列竞品数量。

### 6.3 情感与立场

提及可以被判定为正向、中性、负向、混合或未知。判断必须附带原文片段和置信度；无法可靠判断时应标记为未知，而不能强制二分类。

### 6.4 引用识别

系统提取回答中的 URL、域名、页面标题或结构化引用，并通过规范化和重定向解析判断其属于：

- 品牌官方网站。
- 竞品网站。
- 可信第三方来源。
- 一般第三方来源。
- 无法确认的来源。

引用出现表示回答展示或关联了该来源，不等同于能够证明模型内部一定依赖该来源生成全部结论。

### 6.5 评估质量

Answer Judge 可使用规则、模型或混合方法，但必须通过人工标注集校准，并计算 Precision、Recall、F1 和混淆矩阵。

所有规则、Prompt、模型和代码版本都必须记录。重新评估应产生新版本，不能覆盖旧结果。

## 7. 可见度指标原理

设固定分析范围内的有效回答集合为 `R`。有效回答是请求成功、非空、非纯错误或拒答、未严重截断、语言符合协议且可以解析的回答。

### 7.1 品牌提及率

```text
Mention Rate = 含品牌提及的有效回答数 / 有效回答总数 × 100%
```

它表示品牌被谈及的频率，但不代表品牌得到推荐。

### 7.2 品牌推荐率

```text
Recommendation Rate = 主动推荐品牌的有效回答数 / 有效回答总数 × 100%
```

推荐必须存在明确的建议语义，不能把普通列举计为推荐。

### 7.3 官方引用率

```text
Official Citation Rate = 引用品牌自有域名的有效回答数 / 有效回答总数 × 100%
```

可信第三方引用率应单独计算，不能与官方引用率混合。

### 7.4 正向提及率

```text
Positive Mention Rate = 正向提及品牌的回答数 / 含品牌提及的有效回答数 × 100%
```

分母采用含品牌提及的回答数，可以反映品牌在被讨论时的正向程度。报告必须明确展示该口径。

### 7.5 统计可信度

系统同时展示：

- 指标分子和分母。
- 样本量。
- 95% Wilson 置信区间。
- 测试协议及版本。
- 数据缺失和无效回答数量。

跨问题汇总时，默认提供“按回答等权”和“按问题等权”两种视图，避免因某些问题采样次数更多而主导总指标。

## 8. 内容缺口识别原理

系统联合比较以下数据：

1. 品牌知识库和已确认实体关系。
2. 企业网站页面及内容片段。
3. 竞品页面和主题覆盖。
4. AI 搜索回答中的提及、推荐和观点。
5. AI 回答展示的外部引用来源。

系统据此识别：

- 缺失的主题和用户问题。
- 未被清晰说明的产品功能。
- 缺失的应用场景、行业方案或客户类型。
- 缺少数据、研究、案例或可验证来源的结论。
- 页面结构不适合直接提取答案。
- 官网内部或官网与第三方之间的信息冲突。
- 竞品拥有而品牌缺少的内容和权威性信号。

每条缺口必须关联具体问题、页面、回答、竞品或引用证据，不能只给出无法解释的综合分数。

## 9. 优化执行原理

诊断结果首先转换为结构化任务，而不是直接修改生产环境。任务包含：

- 优化目标和目标指标。
- 问题来源与证据。
- 建议修改的页面或结构化数据。
- 预计影响和风险。
- 负责人、截止时间和验收条件。
- 后续验证方案。

Optimization Agent 可以生成内容、页面结构或 JSON-LD 草稿，但执行链路必须为：

```text
生成草稿
   ↓
事实、引用、链接、Schema 和安全校验
   ↓
生成可查看的 Diff
   ↓
有权限的人员审批
   ↓
创建 Pull Request 或执行发布
   ↓
发布后健康检查
   ↓
效果验证或失败回滚
```

网页内容属于不可信输入，不能通过页面中的指令改变 Agent 的系统规则、读取密钥或触发发布操作。Agent 不得伪造数据、研究、客户案例、用户评价或媒体报道。

## 10. 效果验证原理

### 10.1 实验假设

每次优化应事先定义可验证假设，例如：

> 在产品页增加明确的私有化部署能力、技术条件和客户案例后，与私有化部署相关的问题中，品牌推荐率将在固定测试协议下提高。

### 10.2 实验设计

实验需要冻结：

- 实验假设和目标指标。
- 测试问题集。
- 模型、渠道、语言和地区。
- 实验组与对照组。
- 采样次数、周期和停止条件。
- Judge 和指标算法版本。

### 10.3 结果判断

系统不能只展示一个涨跌百分比，还应展示：

- 实验前后样本量。
- 指标差值和效应量。
- 置信区间。
- 无效或缺失样本。
- 模型、协议和外部环境变化。
- 实验设计是否能够支持因果判断。

最终结论可以是有效、无显著变化、负向、数据不足或协议失效。一次回答的变化不能作为优化成功的证据。

## 11. 数据与可复现性原理

系统采用“原始证据不可变、派生结果可重算”的设计：

```text
原始网页/AI 回答
        ↓
版本化解析结果
        ↓
版本化实体与评估结果
        ↓
版本化聚合指标
        ↓
报告、诊断和优化任务
```

每个派生结果都要记录输入数据 ID、算法版本、配置哈希和生成时间。算法升级时生成新的评估版本，使用户能够比较旧算法和新算法的结果。

原始网页、截图和大型回答存放在对象存储中；关系数据、状态和索引存放在 MySQL 中；Redis 用于缓存、限流和异步任务协调。图谱初期可以使用关系表实现，只有在查询规模和关系遍历需求明确后再考虑专用图数据库。

## 12. 安全与治理原理

### 12.1 多租户隔离

所有业务数据必须能够追溯到租户和项目。接口、任务、缓存、对象存储和日志均执行租户隔离，跨租户访问必须被拒绝并留下审计记录。

### 12.2 抓取安全

抓取器必须防止 SSRF，不得访问回环地址、私有网络、链路本地地址或云元数据服务，并且在每次重定向后重新校验目标地址。

### 12.3 密钥保护

模型和 GitHub 等外部服务的密钥必须使用密钥管理系统保存，业务数据库只存引用。日志、错误消息和页面不得显示完整密钥。

### 12.4 生产变更治理

所有自动修改必须具备最小权限、操作日志、人工审批、幂等执行和回滚能力。Agent 默认不得自行批准其生成的变更。

## 13. 技术限制

1. 无法从公开回答确定第三方模型完整的内部检索、召回和排序过程。
2. 模型 API 结果不一定代表消费者应用中的实际搜索结果。
3. 生成式回答具有随机性，必须通过重复采样处理不确定性。
4. AI 平台可能在没有通知的情况下更换模型、索引或产品逻辑。
5. Schema、内容结构和第三方权威信号只能提高机器理解与引用的可能性，不能保证推荐。
6. 相关性变化不自动构成因果关系，实验设计决定结论强度。
7. 外部内容的采集和使用受到 robots、服务条款、版权和隐私法规约束。

## 14. 核心结论

GEO Intelligence 的技术核心不是寻找一个所谓的“AI 排名技巧”，而是把品牌在 AI 搜索环境中的表现变成可以采集、解释、优化和验证的工程问题：

> 用可追溯数据建立品牌知识模型，用受控的重复实验测量 AI 搜索表现，用证据驱动内容和技术优化，再通过版本化评估验证变化是否真实有效。
